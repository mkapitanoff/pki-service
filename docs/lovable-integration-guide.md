# Гайд: интеграция с Chandra (PKI-сервис подписания) через Lovable

Этот файл — для коллеги, который подключает свой Lovable-проект к Chandra. Отдайте ему этот
файл целиком; раздел **«Промпт для Lovable»** можно скопировать и вставить прямо в чат агента
Lovable — этого достаточно, чтобы получить рабочую интеграцию за один проход.

Тенант и API-ключ выдаются отдельно командой Chandra — в промпте ниже для них оставлены плейсхолдеры.

---

## Что такое Chandra

PKI-сервис подписания документов ЭЦП РК (`https://pki.fin4b.kz`). Модель: клиент присылает
хэш документа + CMS-подпись (сформированную через NCALayer на компьютере пользователя), Chandra
проверяет подпись, штампует QR-код и Лист подписей на PDF, кладёт готовый файл в S3 клиента.

**Важно понимать сразу**: подписание — двухфазное и асинхронное:
1. `/sign/complete` подтверждает подпись **криптографически** и отвечает быстро (доли секунды —
   секунды на документ).
2. Штамповка QR + пересборка Листа подписей + выгрузка готового PDF в S3 клиента идёт **в фоне**
   (ещё несколько секунд, зависит от числа страниц) — это отдельный шаг, за которым надо следить
   через `GET /sign/status`.

Полный технический контракт — `docs/integration.md` в этом репозитории (или
`https://pki.fin4b.kz/api/docs/integration.md`). Этот файл — практическая выжимка + готовый
промпт для Lovable, учитывающая ошибки, которые мы уже словили на других интеграциях.

## Промпт для Lovable

Скопируйте всё между линиями `-----` и вставьте в чат агента Lovable-проекта, куда подключаете
Chandra. Перед вставкой замените `<TENANT_API_KEY>` на реальный ключ (когда получите).

-----

Нужно реализовать подписание документов через PKI-сервис Chandra (`https://pki.fin4b.kz`,
`Authorization: Bearer <TENANT_API_KEY>`). Модель — «hash-flow»: клиент отправляет только хэш
документа, подпись формируется локально через NCALayer, дальше Chandra всё делает сама.

### 1. Загрузка исходных документов — presigned PUT напрямую в S3, БЕЗ base64 через edge-функцию

Не читай PDF в base64 и не отправляй его целиком в теле запроса edge-функции — на тяжёлых
многостраничных документах (30-100+ МБ) это гарантированно упрётся в лимит памяти Deno runtime
(`Memory limit exceeded`, HTTP 546).

Правильный паттерн:
1. Edge-функция принимает только метаданные документа (`name`, `size`, `content_type`) — тело
   запроса маленькое (килобайты).
2. Edge-функция генерирует 3 presigned URL и отдаёт их клиенту: `source_put_url` (PUT — клиент
   грузит оригинал), `source_url` (GET — передаётся Chandra), `target_url` (PUT — Chandra
   выгружает туда готовый файл).
3. Клиент грузит файл `fetch(source_put_url, {method: "PUT", body: file})` напрямую в S3, минуя
   edge-функцию как прокси тела запроса.
4. Убедись, что CORS на S3-бакете разрешает `PUT` с origin приложения — иначе прямая загрузка из
   браузера упадёт с `Failed to fetch`.

### 2. Хэш документа — считать сразу при загрузке, не откладывать на момент подписания

Сразу после загрузки в S3 (шаг 1) посчитай SHA-256 содержимого и запиши в метаданные объекта
(`x-amz-meta-sha256`). Это даёт fast-path на `/sign/initiate` — Chandra не должна ничего сама
скачивать и хэшировать (что было бы медленно и не масштабируется на тяжёлые файлы).

### 3. `POST /api/v1/sign/initiate`

```json
{
  "signer_role": "client",
  "application_id": "<ваш внутренний ID заявки>",
  "documents": [{
    "name": "agreement.pdf",
    "client_ref": "doc-001",
    "source_url": "<presigned GET>",
    "target_url": "<presigned PUT>",
    "target_s3_key": "signed/<app_id>/agreement.pdf",
    "hash": "<base64 SHA-256 точных байт, залитых в S3>",
    "hash_algorithm": "SHA256",
    "s3_bucket": "<бакет исходника>",
    "s3_key": "<ключ исходника>"
  }]
}
```
Заголовок `Idempotency-Key: <свежий UUID>` — **новый на каждую попытку пользователя**, не
выводить из `application_id`/имён файлов/содержимого — иначе повтор с другим содержимым получит
устаревший ответ прошлой попытки (409 `IDEMPOTENCY_KEY_REUSED`, если тело отличается).

Ответ: `{ session_id, documents: [{ doc_id, hash, status: "ready" }] }`.

### 4. NCALayer — подпись хэша на устройстве пользователя

`kz.gov.pki.knca.basics.signHashes([hash], { digested: true, format: "cms" })` — один вызов на
весь пакет документов сразу, не по одному (иначе пользователь вводит ПИН несколько раз).

### 5. `POST /api/v1/sign/complete`

```json
{ "session_id": "…", "signatures": [{ "doc_id": "…", "cms": "<base64 CMS от NCALayer>" }] }
```
Ответ приходит быстро и означает **только** «подпись криптографически подтверждена», НЕ «файл
готов к скачиванию»:
```json
{ "succeeded": 3, "failed": 0, "documents": [{ "doc_id": "…", "name": "…", "status": "signed" }] }
```
`s3_key` в этом ответе намеренно отсутствует.

### 6. `GET /api/v1/sign/status/{session_id}` — поллинг

Per-doc `state`: `PENDING → FETCHING → READY → SIGNING → SIGNED → UPLOADING → UPLOADED` |
`FAILED`. Дополнительные поля: `verify_url`, `s3_key`, `error_code`
(`FETCH_FAILED`/`UPLOAD_FAILED`/`SIGNING_FAILED`/`POST_PROCESSING_FAILED`/`TARGET_URL_EXPIRED`/`TARGET_URL_REJECTED`).

**Гейтинг UI — два независимых условия, не путать:**
- **Кнопка/ссылка «Проверить подпись» (verify_url) + QR** — показывать сразу, как только у
  документа появился непустой `verify_url` (это уже `state=SIGNED`). НЕ ждать `UPLOADED`.
- **Кнопка «Скачать»** — задизейблена (с лоадером вместо иконки), пока `state ≠ UPLOADED`.
  Активна только при `state=UPLOADED`, когда `s3_key` заполнен.

**Поллинг:**
- Интервал 2 секунды достаточен, backoff не обязателен.
- ОБЯЗАТЕЛЬНО ограничить максимальное время автополлинга (например, 5-10 минут) — по истечении
  остановить и показать пользователю кнопку «Обновить статус» вместо тихого бесконечного цикла.
- Если документ «работает» (`SIGNING`/`UPLOADING`) дольше ~30 секунд — покажи нейтральную
  подсказку «обработка больших документов может занять больше времени», а не голый спиннер без
  контекста (иначе выглядит как зависание).
- НЕ делай повторное скачивание+пересчёт хэша исходника на клиенте после `/sign/initiate» «для
  проверки» — если используется client-hash fast-path (шаг 2), это лишний трафик и время, Chandra
  уже асинхронно сверяет `x-amz-meta-sha256` сама.

**Обработка ошибок:**
- `error_code: TARGET_URL_EXPIRED` — presigned URL истёк раньше, чем закончилась фоновая
  обработка. Восстановимо: сгенерируй новый `target_url` и вызови `PATCH /sign/refresh-urls`,
  выгрузка повторится автоматически без пересборки PDF.
- `error_code: TARGET_URL_REJECTED` — presigned `target_url` отклонён S3 клиента с 403, но НЕ по
  истечению (обычно `SignatureDoesNotMatch`): запрос Chandra не совпал с подписью URL. Перевыпуск
  через `refresh-urls` НЕ поможет — проблема в контракте самого presigned PUT. Частая причина:
  target-presign подписан с обязательным `x-amz-meta-sha256`, которого Chandra при заливке не шлёт
  (для target подписывай presign БЕЗ метаданных, только `Content-Type`). Покажи ошибку, ретрай не
  предлагай — нужно исправить генерацию `target_url`.
- `error_code: POST_PROCESSING_FAILED` — терминально, фоновая сборка/выгрузка исчерпала попытки
  на стороне Chandra. Покажи понятную ошибку, кнопку ретрая с фронта не делай (нужно
  переподписание документа заново).

**Ошибки верификации подписи — из `POST /api/v1/sign/complete`** (per-doc `status != "signed"` +
`error`, либо HTTP 422 `{"error":{"code":"…"}}`). Соответствуют Правилам НУЦ РК (приказ №1187):
- `CMS_INVALID` — подпись криптографически невалидна (хэш не совпал / битый CMS). Терминально.
- `CERT_REVOKED` — сертификат отозван. Терминально.
- `CERT_INVALID_USAGE` — выбран сертификат аутентификации (нет `nonRepudiation`/«Неотрекаемость»)
  вместо сертификата подписи. Сообщение: «Выберите сертификат для подписи (ключ RSA…SIGN или
  GOST…SIGN)». Дай повторить с правильным ключом.
- `CERT_STATUS_UNKNOWN` — не удалось подтвердить статус отзыва (OCSP НУЦ РК временно недоступен).
  ВРЕМЕННО. Сообщение: «Сервис НУЦ РК недоступен, попробуйте через минуту» + кнопка «Повторить».

### 7. Модалка/UI подписания

Модалка должна закрываться сразу, как только `/sign/complete` вернул успех по всем документам
(`state=SIGNED`) — не дожидаясь `UPLOADED` внутри модалки. После закрытия — статус-бейдж,
verify-ссылка и кнопка «Скачать» продолжают обновляться уже на странице (списке документов
заявки), через тот же поллинг `/sign/status`, до финального `UPLOADED`/`FAILED`.

### 8. Тестирование

Прогони как минимум: (а) один мелкий PDF, (б) один тяжёлый многостраничный PDF (30+ МБ,
50+ страниц) — специально чтобы проверить, что presigned-загрузка и поллинг не упираются в
лимиты; (в) намеренно испорченный `target_url`, чтобы увидеть `TARGET_URL_EXPIRED` и восстановление
через `/refresh-urls`.

## Чек-лист для проверки после того, как Lovable всё реализует

- [ ] Загрузка исходников идёт через presigned PUT напрямую в S3, не через base64 в теле edge-функции.
- [ ] Хэш считается сразу при загрузке (fast-path), не откладывается на момент `/sign/initiate`.
- [ ] `Idempotency-Key` — свежий UUID на каждую попытку подписания.
- [ ] Модалка закрывается сразу по `SIGNED`, не блокирует пользователя до `UPLOADED`.
- [ ] Verify-ссылка/QR показываются с `state=SIGNED`, кнопка «Скачать» — только с `UPLOADED`.
- [ ] Поллинг статуса ограничен по времени (не бесконечный).
- [ ] Тест с тяжёлым многостраничным PDF прошёл без ошибок и таймаутов.
- [ ] `/verify/{doc_id}` открывается и показывает корректные данные подписанта.

## Смоук-тесты перед первым подписанием

Прогоните это ДО попытки реального подписания — большинство проблем интеграции ловятся здесь,
без необходимости трогать NCALayer/ЭЦП-ключ.

### 1. Chandra доступна и здорова
```bash
curl -s https://pki.fin4b.kz/health
```
Ожидается `{"status":"ok", ...}`.

### 2. API-ключ валиден (без побочных эффектов)
```bash
curl -s -H "Authorization: Bearer <TENANT_API_KEY>" https://pki.fin4b.kz/api/v1/webhooks
```
Ожидается `200` с (возможно пустым) списком, НЕ `401 UNAUTHORIZED`. Если `401` — ключ
неверный/неактивный, дальше двигаться бессмысленно.

### 3. S3-бакет: presigned GET/PUT реально работают
- Сгенерировать presigned PUT из вашей edge-функции, залить тестовый маленький PDF **напрямую
  из браузера** (не из бэкенда) — это единственный способ проверить CORS по-настоящему.
- Сгенерировать presigned GET на тот же ключ, скачать содержимое — байты должны совпасть.
- Убедиться, что PUT-запрос из браузера не падает с CORS-ошибкой (`Access-Control-Allow-Origin`)
  — если бакет настраивали недавно, обязательно перепроверить именно из браузерного origin
  приложения (preview и prod домены Lovable могут отличаться — проверить оба).

### 4. Хэш и метаданные совпадают
После загрузки тестового PDF в S3 (шаг 3) — прочитать `x-amz-meta-sha256` объекта (через `HEAD`)
и сверить с SHA-256, посчитанным на клиенте перед загрузкой. Должны совпасть побайтово (в hex,
регистр не важен, но кодировка — если base64, а не hex, свериться, что `/sign/initiate` получит
именно тот формат, который ожидает `hash_algorithm: "SHA256"` — Chandra принимает base64).

### 5. `/sign/initiate` — сухой прогон без реальной подписи
Отправить настоящий `POST /sign/initiate` с одним тестовым документом (реальные `source_url`,
`target_url`, `hash` из шагов 3-4). Ожидается `200` и `status: "ready"` для документа. Это
проверяет весь путь: аутентификация → доступность вашего S3 для Chandra (она скачивает по
`source_url` в фоне для кэша) → корректность payload'а. Реальную подпись на этом шаге отправлять
не нужно — сессию можно оставить незавершённой, она сама протухнет по TTL.

### 6. NCALayer доступен в браузере
- Плагин/приложение NCALayer запущено локально (обычно `wss://localhost:13579`).
- В браузере есть хотя бы один валидный сертификат ЭЦП (тестовый или боевой) для проверки вызова
  `signHashes` — на этом шаге НЕ обязательно подписывать документ из шага 5, достаточно убедиться,
  что диалог NCALayer вообще открывается и видит сертификат.

### 7. `/verify/{doc_id}` отдаёт 404 для несуществующего ID (не 500)
```bash
curl -s -o /dev/null -w "%{http_code}\n" https://pki.fin4b.kz/verify/00000000-0000-0000-0000-000000000000
```
Ожидается `404`. Если `500`/timeout — что-то не так с самим сервисом, эскалировать до реального
теста подписания.

Если все 7 пунктов прошли — можно переходить к реальному тесту подписания (маленький файл →
затем тяжёлый многостраничный, как описано в промпте выше).

### Дополнительно: проверка нового бакета `fin4b-invd`

Свежий бакет — CORS почти наверняка не настроен по умолчанию, curl этого не покажет (CORS
проверяется только реальным браузером). Прогнать именно на `fin4b-invd`:

- [ ] **CORS-политика бакета** задана явно: `AllowedMethods: ["PUT","GET"]`,
      `AllowedOrigins` включает ОБА origin — preview-домен Lovable (`https://id-preview--*.lovable.app`
      или `https://preview--*.lovable.app`, в зависимости от того, какой реально открыт в браузере)
      И прод-домен приложения. Забыть один из двух — самая частая причина `Failed to fetch`
      именно на новом бакете.
- [ ] `AllowedHeaders` разрешает кастомные заголовки, которые шлёт presigned PUT (как минимум
      `x-amz-meta-sha256`, `Content-Type`) — если список не `["*"]`, перечислить явно.
- [ ] Presigned PUT сгенерирован **на `fin4b-invd`** (не на старом бакете по ошибке
      скопированного конфига) и реально выполнен `fetch(url, {method:"PUT", body:file})`
      **из браузера** (preview-домен), не curl'ом — именно так поймаете CORS-ошибку, если она есть.
- [ ] После PUT — `HeadObject` на тот же ключ показывает `x-amz-meta-sha256`, совпадающий с
      хэшем, который посчитали на клиенте до загрузки.
- [ ] Presigned GET с `fin4b-invd` по тому же ключу отдаёт те же байты (сверить размер/хэш).
- [ ] Region/endpoint `fin4b-invd` совпадает с тем, что зашито в конфиг S3-клиента приложения —
      если бакет создан в другом регионе, presigned-подпись (SigV4) будет невалидна без явного
      указания региона.
- [ ] Реальный `/sign/initiate` с `source_url`/`s3_bucket: "fin4b-invd"` — Chandra должна суметь
      скачать оттуда документ (не только вы сами) — это же новый бакет, у Chandra нет истории
      обращений к нему, первый реальный запрос покажет любые проблемы с доступом/правами.

## Онбординг (тенант + ключ)

Тенант и API-ключ заводит команда Chandra отдельно — ничего в коде Chandra под этого клиента
дорабатывать не нужно. После получения ключа — просто подставить его в конфиг/секреты
Lovable-проекта (`Authorization: Bearer <ключ>`).

## Если что-то не работает

Пришлите: `X-Request-Id` из ответа (или заголовок запроса, если сами его передавали), время
(UTC) и какой именно эндпоинт — по этим данным можно поднять логи Chandra и разобраться быстро.
